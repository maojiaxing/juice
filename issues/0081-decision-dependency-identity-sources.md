## Question

以前置 [包、模块与产物模型](0080-decision-package-products-defaults.md) 确定的提供方面为输入；参考 [Cargo 语义研究](0078-research-cargo-package-semantics.md) 与 [Zig 分工研究](0079-research-zig-package-semantics.md)。

依赖引用怎样分别表达导入名、提供方包身份、导出模块选择、来源和版本/修订约束，使“写明的来源不会被同名成员覆盖”成为可验证的契约？

需决定本地路径、Git、工作区引用的互斥形状与缺省行为；多来源/缺来源/相对路径基准/别名冲突的错误规则；Git 仓库内选包及固定修订与版本约束的关系；是否需要锁定结果来完成本轮可复现语义，以及明确不支持哪些组合。普通依赖、仅测试/构建用途的依赖或依赖传递是否需要分开，应基于实际案例决定而非照搬。

提供方模型已经关闭，完整前提以 [包、模块与产物模型的决定](0080-decision-package-products-defaults.md#resolution) 为准。需补齐：一个依赖引用如何选择一个或多个模块导出、是否存在默认导出、导入别名及同包模块引用如何处理；不因为包名相同而默认唯一模块，也不因提供多个模块而自动注入全部模块。无公开模块的包作为依赖时能否用于工具或其他用途，也须明确能力匹配与失败规则。

案例至少覆盖显式 Git 与同名成员共存、导入别名、一个来源的多个包/模块、路径移动、错误修订，以及缺少工作区上下文。完成条件：声明到唯一来源身份与导出选择的规则、失败表和能力边界无歧义；不实施下载器、求解器或锁文件。

### 第四轮：Dependency 只表达消费方引用

用户先问“是否在原来的 dependency 上增加一个 modules 或 packages 字段列表就好”，随后纠正：“dependency 只做引用，并不关注引用的 monorepo 下有多少个模块”。

### 第五轮：扁平引用、包目录 path 与唯一根模块简写（已确认）

用户先询问引用列表是否需要 path、单模块仓库能否省略 modules，又确认根包的引用方法，最后明确回复“按照以上方案进行定义”。本轮为引用形态的权威阶段决定，替代第一轮的一依赖一包限制、第二轮的禁止单模块简写；不采用独立 monorepo 变体或 packages[].modules 嵌套。

#### 字段职责

| 字段 | 已确认语义 |
|---|---|
| `Dependency.name` | 当前包内的依赖引用名，不是提供方包名，也不自动变成导入别名 |
| `Dependency.source` | 唯一的显式来源（path / git / workspace）；取得引用基准目录 |
| `Dependency.modules` | 消费方实际需要的模块选择列表，不枚举上游全部包或模块 |
| `modules[].path` | 相对来源根目录的包目录，省略或 `"."` 都指来源根；目录应有 package.jai |
| `modules[].name` | 该包公开声明的模块导出名；第六轮确认可以省略，但目标包必须恰有一个公开模块 |
| `modules[].alias` | 可选的消费方导入名，省略时沿用模块导出名 |

- 引用列表扁平表达所需选择；不同项可以使用不同包目录，也可以从同一包选择不同导出。Dependency 不记录上游有多少包或模块，不因未引用成员变化而改写声明。
- path 定位包含 package.jai 的包目录，不指向 `.jai` 文件，不允许绕过提供方清单；实际入口由该包的 modules 声明解析获得。
- path/name 无效、清单缺失或导出不存在时直接报错，不尝试其他目录或按包名递归搜索。
- Git 来源仍遵守已确认的 branch/tag/rev 最多选一个，全部省略时引用默认分支；更新时机另议。
- 本地 `source.path` 相对消费方声明包根定位；选择项的 `modules[].path` 再相对取得的来源目录定位。两种 path 不能混用基准。
- 第五轮时 workspace 引用基准未定；第八轮确认采用声明包所属工作区根，且所选包必须属于该工作区，详见下文。

#### 根包与省略规则

| `modules` 配置 / 来源根状态 | 结果 |
|---|---|
| 显式项 path 省略或为 `"."` | 读取来源根 package.jai，按项的 name 选择导出 |
| 整体省略 modules，来源根包恰有一个公开模块 | 引用唯一模块，导入名沿用其导出名 |
| 整体省略 modules，来源根包有多个公开模块 | 报歧义，要求显式选择，不按包名、首项或目录顺序猜测 |
| 整体省略 modules，来源根没有包、只有工作区 | 要求显式成员位置，不递归寻找唯一成员 |
| `modules = []` | 明确不引用模块，不触发唯一模块简写；第九轮确认普通导入依赖因此报能力不匹配，工具/插件用途交专门票 |
| 来源根包同时管理工作区成员 | 根包引用不自动包含成员；唯一性仅检查根包导出，不统计整个仓库 |

第五轮结束时，零公开模块的错误、选择项 name 是否也可省略及引用冲突尚未确认；第六轮随后明确了这些规则，第九轮补齐同模块多别名与提供方身份规则。

#### 语义示例（不是已验证的 Jai 类型实现）

根包显式模块：

```jai
.{
    name = "toolkit_dep",
    source = .{ git = .{ url = "https://example.com/toolkit.git" } },
    modules = .[
        .{ path = ".", name = "Toolkit" },
    ],
}
```

根包恰好一个模块时简写；成员多少不影响简写：

```jai
.{
    name = "toolkit_dep",
    source = .{ git = .{ url = "https://example.com/toolkit.git" } },
}
```

只引用两个所需模块，不描述整个 monorepo：

```jai
.{
    name = "toolkit_dep",
    source = .{ git = .{
        url = "https://example.com/toolkit.git",
        branch = "main",
    } },
    modules = .[
        .{ path = "packages/codec", name = "Codec_Json", alias = "Json" },
        .{ path = "packages/parser", name = "Parser" },
    ],
}
```

#### 与先前决定的关系及剩余问题

- 保留来源显式互斥、相对路径基准、不覆盖同名来源、引用名/包名/导出名/导入名分离。
- 调整为“Dependency 引用一个来源下所需模块”，而不是固定一个提供方包；每个模块选择仍从一个有清单的具体包获得导出。
- 单模块简写只认来源根包，新增第二个根模块会令简写报歧义；显式选择不受新增无关导出影响。这是用户接受的简洁性取舍，不得变成自动导入全部。
- 第五轮尚有 Git 更新、引用冲突、成员简写等边界待定；后续轮次的确认见下文。具体 Jai 类型与省略/空列表区分交声明校验票。

### 第六轮：Git 不自动追新、导入冲突、成员简写与路径边界（已确认）

用户对本轮 Q9–Q12 明确回复“按推荐”：

9. Git 依赖首次解析时取得声明的分支、标签或修订所对应的提交；普通 build/run/test 复用已解析提交，不自动追随远端变更。仅显式更新或改变来源声明才重新选择。这里定义选择时机，不等于禁止按同一提交补充下载缺失对象；解析结果存放方式、离线和缓存缺失行为待下一轮。
10. 同一个消费包内，所有依赖模块引用按最终导入名（alias，否则为选中导出名）统一判重；重复、仅大小写不同、完全重复的引用项都报错，不按声明顺序覆盖。不同来源都导出 Json 时须由消费方改别名。同一模块使用不同别名是否允许，以及自有模块/编译器内置名称如何参与检查，仍待后续决定。
11. 显式选择项可以省略 name，包括成员包；按 path 定位的包恰有一个公开模块时选中它，零个时报“没有可引用模块”，多个时报歧义。根包整体省略 modules 同样遵守零/一/多规则；不递归查其他包、不按包名猜测。alias 可独立给出，例如 { path = "packages/codec", alias = "Codec" }。显式 modules = [] 仍不触发简写；空模块用途是否允许另议。
12. modules[].path 必须是来源根内的相对包目录，不接受绝对路径或规范化后越出来源根的路径；需要兄弟来源时明确声明 source.path。路径存在性、清单与公开导出继续校验。符号链接等同一性与包含关系的具体算法交声明校验票，不能因此绕过来源边界。

### 第七轮：暂不引入锁文件，精确补充下载与本地实时内容（部分确认）

用户回复“q14 是，q16 是，q13 暂时不……lock 文件，保持简单实现，q15 需要详细解释与讨论”。

### 第八轮：保留 workspace 成员约束，普通 path 并存（已确认）

用户确认“保留这层约束”，并询问普通路径是否继续可用；普通 path 继续保留，与 workspace 并列而非被取代。

15. workspace 来源是带工作区约束的本地引用：来源根为声明包所属的工作区根；modules[].path 相对该根定位；所选包必须属于该工作区。缺工作区上下文或所选目录不是成员则报错，不自动改为 path 引用。
16. 普通 path 来源仍按声明依赖的包根解析，本地目标不要求具有工作区成员资格；可以引用工作区成员，也可以引用不在工作区的有效包。选用 path 不会仅因目标恰好是成员而切换来源语义。
17. 两种来源都保留目标包清单、公开导出、引用名冲突及来源内模块路径等校验，并直接使用本地当前文件。模块相对路径不能越出已选来源根；访问兄弟目录须通过明确的 source.path 选择来源。
18. workspace 不自动引用全部成员、不自动继承成员依赖、不覆盖显式 Git 或 path 来源、不根据命令启动 cwd 改变声明包的所属上下文。外部 Git monorepo 仍用 git 来源加显式模块选择路径，不解释成消费方的本地工作区。

以 apps/cli 引用 packages/codec 为例，path 写为 source.path = "../../packages/codec"；workspace 则以工作区根为来源根，modules 项 path = "packages/codec"。两者可指向相同包，但前者表达本地位置，后者另外保证成员关系。若 vendor/other 有合法清单但不是成员，path 可以引用，workspace 必须拒绝。

工作区归属查找、根包是否计入成员、嵌套与排除规则由工作区决策票确定；依赖票只消费明确的所属根与成员集合，不在这里重写发现算法。

第八轮结束时仍有本机解析状态、身份与模块可见性等问题；后续确认见下文。

### 第九轮：本机解析缓存、清单身份与包内模块可见性（已确认）

### 1. 引用形态与字段职责

一条 Dependency 从一个显式来源选择消费方需要的公开模块；扁平选择项可以来自该来源中的不同包。不增加 monorepo 变体，不使用 packages[].modules 嵌套，不枚举上游全部成员或模块。

| 字段 | 统一语义 |
|---|---|
| `Dependency.name` | 消费包内唯一的依赖引用名；不是提供方包名，不自动成为导入名 |
| `Dependency.source` | 必须且只能选择 path、git、workspace 一种来源 |
| `Dependency.modules` | 消费方模块选择；整体省略有唯一根模块简写，显式空列表不触发简写 |
| `modules[].path` | 相对来源根的包目录；省略或 `"."` 指来源根，不是源码文件路径 |
| `modules[].name` | 提供方模块导出名；省略时目标包必须恰有一个公开模块 |
| `modules[].alias` | 可选的最终导入名；省略时沿用选中导出的名字，不使用 Dependency.name |

每个被引用的普通包必须有有效 package.jai。清单定义包身份和公开导出；源码 entry 只由提供方确定，消费方不能指定文件绕过清单。路径、清单或导出无效直接失败，不搜索其他目录、不按包名递归找包、不回退到同名工作区成员或注册中心。

提供方 `Package.modules` 定义模块，消费方 `Dependency.modules` 选择模块；同名字段不代表同一职责。具体 Jai 类型与省略/空列表的可靠表达交声明校验票。

### 2. 来源定位与边界

| 来源 | 来源根及约束 |
|---|---|
| 本地 path | 相对 source.path 以声明依赖的包根为基准；允许兄弟目录，不要求目标是工作区成员 |
| git | 声明仓库在已解析提交上的检出根；不按包名在仓库内搜索 |
| workspace | 声明包实际所属工作区的根；所选包必须是成员，缺上下文或成员资格时报错 |

- 所有来源的 modules[].path 必须是来源根内的相对包目录；拒绝绝对路径和规范化后越界，不受命令 cwd 影响。
- path 与 workspace 并存；本地目标恰好是成员不会使 path 自动切换语义，workspace 失败也不降级为 path。
- 外部 Git 包的内部 workspace 依赖使用提供方在该检出中的所属工作区，查找不越过检出根，不借用最外层消费工程的工作区。同名成员不能替换已声明的 Git 来源。
- Git 获取的包内部 path 引用只允许同一检出内的包；保留仓库及提交身份，不要求成员资格。内部 workspace 引用同样来自该检出选定的内容。跨仓库引用必须显式使用另一个 git 来源。
- 普通本地开发包的 path 仍可跨消费包目录；Git 内部的来源边界不等于限制所有本地引用。
- path/workspace 的本地内容直接使用当前文件，不冻结为 Git 提交或不可变快照；Git 内部相对 path 不因此丢掉原有 Git 来源身份。

具体路径/URI 规范化、符号链接、平台绝对路径判定交声明校验票；工作区成员、根包归属、嵌套和排除规则交工作区票，均不得放宽这里的来源边界。

### 3. 省略、空列表与能力匹配

| 输入 | 结果 |
|---|---|
| 整体省略 modules，来源根包恰有一个公开模块 | 选中唯一模块，沿用导出名 |
| 整体省略 modules，根包零个或多个公开模块 | 分别报“没有可引用模块”或歧义 |
| 整体省略 modules，只有工作区而无根包 | 要求显式成员位置，不寻找唯一成员 |
| 显式选择项省略 name | 只在该项 path 定位的包内按零/一/多规则选择 |
| 显式选择 name | 必须匹配该包公开导出，不猜默认项 |
| modules = [] | 明确零选择；普通导入依赖报能力不匹配，不自动导入全部 |
| 根包同时管理成员 | 不自动引用成员，也不把成员模块计入根包唯一性 |

唯一模块简写接受“新增第二个公开模块会变为歧义”的取舍；需要不受新增导出影响时使用显式 name。零公开产物的包本身仍合法；工具、插件、构建辅助用途的声明和能力校验由专门票定义，不能用空模块列表隐式启用。

### 4. 身份、别名与重复

- 提供方身份从目标清单及其来源取得。Dependency.name 不断言提供方包名，不另增重复的 package 字段。路径改指另一个合法包且所选导出仍有效时，不额外报包名身份不匹配。
- Git 包的逻辑身份包含规范化仓库来源、已解析提交、仓库内包目录；模块再由该包的公开导出名确定。消费方引用名和 alias 不参与提供方身份。
- 本地 path/workspace 先各自验证来源资格，再以最终规范化包目录确定包同一性；同一路径不因引用写法不同变成两个包。不同目录仅仅包名或本地 Git HEAD 相同不合并。
- 同一消费包对同一实际模块最多选择一次，跨 Dependency 或使用不同 alias 也报重复。选择同包的不同模块允许。
- 同名但来源或已解析提交不同的包可并存，用不同引用名和必要的 alias 区分，不自动合并或择新。两个选择器最终落到同一 Git 来源、提交、包和导出时仍报重复。不同修订的类型与模块状态不承诺可互换。
- 最终导入名为显式 alias，否则为导出名。所有依赖导入名在消费包内统一判重，也不得覆盖本包模块或编译器标准模块；仅大小写不同仍是冲突。消费者优先用显式 alias 解决，不自动生成别名、不按声明顺序覆盖。
- 依赖引用名的合法字符和比较算法、URI/路径及模块同一性的具体算法交声明校验票；不得把名称别名当作绕过重复检查的身份。

### 5. 包内与传递依赖可见性

- 外部模块只有被消费包直接声明并选择后才能直接导入。App -> Http -> Crypto 不自动让 App 导入 Crypto；App 直接使用 Crypto 时须自己声明。
- Http 内部所需依赖由 Http 自身声明并解析；最外层消费者不重述完整传递依赖。准备所需依赖不等于把它们全部公开给消费者。
- 同包公开模块可按提供方导出名相互引用。消费者只选择 Codec 时，Codec 可使用同包 Core，但 Core 不因此变成消费者可直接导入的模块。
- 普通依赖为包级一份，供本包模块、程序、测试使用；本轮不增加逐模块、test_dependencies 或 build_dependencies。工具/插件/构建脚本的专门用途不由普通依赖隐式激活。
- 声明包的直接依赖图必须无环；失败报告完整环路。不用加载顺序、隐式提升或重复 shim 解环。包内模块引用不作为包级环判断，是否允许由 Jai 编译规则验证。
- 编译器标准模块不是普通包依赖。当前实现的全局 shim 搜索目录不能被视为已经满足包内导入隔离；具体编译适配仍须在后续验证。

### 6. Git 选择器与版本范围

branch、tag、rev 最多选择一个；都省略时选仓库默认分支。不强制用户填写完整提交哈希。修订必须能确定所需提交，失败不猜替代来源或版本。

本轮不引入独立 Dependency.version、包版本范围求解或提供方包名断言。Git tag 只是修订选择器，不自动校验清单包版本；包版本元数据与 Git 修订分开。旧 version/package 字段必须有明确迁移或拒绝说明，不静默忽略。

### 7. 解析上下文、普通构建与显式更新

解析选择属于发起消费工程的上下文，并区分声明依赖的包和来源选择器。至少按消费/声明包根隔离；共享源码路径不足以标识上下文。同一工作区成员可各自选择不同提交；两个工程共享 Http 检出，也不能共享 Http 的传递依赖选择。全局缓存只复用内容，不决定各工程选择。

| 操作或变化 | 提交选择行为 |
|---|---|
| 普通 build/run/test，已有有效匹配记录 | 复用已选提交，不访问远端追新 |
| 已选提交的内容缺失 | 在线只补充取得该提交；失败不换成分支最新值 |
| 只改 Dependency.name、alias 或 modules | 在已选提交内重新校验模块；缺导出报错，不自动追新 |
| Git URL/选择器变化、记录缺失或新上下文 | 按声明重新解析；离线受下节限制 |
| 显式更新 | 刷新当前消费包上下文的完整直接/传递 Git 依赖图，不改清单或其他上下文 |
| 工程移动/复制到新规范化根 | 新上下文，不按包名或远程地址继承旧记录；仍可复用全局内容 |
| 命令 cwd 改变但工程根不变 | 不视为工程移动 |

显式更新重新解析分支/标签；完整提交哈希仍指向原提交。首版不提供单条直接或传递依赖的定向更新。工作区批量选包及 update/offline 的具体 CLI 契约交后续票，不能因此扩大更新范围。

### 8. 成功保存、失败与离线

获取、清单求值/校验、模块选择、名称/身份冲突和包级环检查全部通过后，才整体保存当前上下文的新解析状态。任一步失败保留旧状态但本次操作失败，不留下部分选择、不假装使用旧状态即为成功；已下载内容可留在缓存。后续源码编译失败不回滚成功解析的选择。状态损坏或不可读须报错，不能当作首次解析悄悄重建。

| 离线情况 | 结果 |
|---|---|
| 本上下文已有有效选择且全部必要内容齐全 | 复用选择 |
| 无记录，rev 为完整提交哈希且必要内容已缓存 | 可在全图校验成功后建立选择 |
| 无记录，使用分支、标签、默认分支或短 rev | 报错，不用缓存 HEAD 或其他工程的选择猜测 |
| 任一直接/传递依赖缺必需内容 | 报错，不联网、不换版本 |
| 请求刷新远端修订选择 | 报错，不把复用说成更新成功 |

原子保存、并发保护和状态编码由后续票落实；不能弱化完整提交和失败语义。

### 9. XDG 内容缓存与本机状态

借鉴 Cargo 的全局内容复用，不照搬其包含配置等内容的 ~/.cargo。两类目录分别由有效绝对 XDG 值优先控制：

| 内容 | 所有平台的 XDG 位置 | 非 Windows 默认 | Windows 默认 |
|---|---|---|---|
| Git 来源内容缓存 | `$XDG_CACHE_HOME/juice` | `$HOME/.cache/juice` | `%LOCALAPPDATA%/juice/cache` |
| 工程解析选择状态 | `$XDG_STATE_HOME/juice` | `$HOME/.local/state/juice` | `%LOCALAPPDATA%/juice/state` |

- Windows 的 XDG 优先及 LOCALAPPDATA 回退是 Juice 政策，不冒称 XDG 的 Windows 规定。
- 变量未设置/为空时用默认值；相对 XDG 值视为无效、警告并回退，不相对 cwd 解释。
- 有效绝对目录不能创建或写入时报错，不偷偷换位置。无法确定可靠默认用户目录时也失败，不使用 cwd、系统根或临时目录兜底。
- 清理源码内容不删除选择状态；明确删除状态后才按缺记录规则重新解析。记录不放入仓库锁文件，不自动搬迁到新工程根。
- 全局 Git 检出只读使用；编译产物、生成源码和插件改写结果放工程私有派生目录，不回写共享内容。具体派生布局由构建定制票定义，不要求本轮设计复杂的 OS 权限机制。

本票不引入 juice.lock，不保证不同机器、状态被删除后或工程移动后自动选中同一浮动修订。path/workspace 的本地修改仍实时生效；锁定 Git 的本机选择不锁定所有输入。

### 10. 典型引用示例

以下仅为 Jai 风格语义草图，尚未完成类型表达与编译验证；省略、显式空列表的最终写法由声明校验票决定。

```jai
// 一个来源，只选根包及两个成员包中的所需模块。
.{
    name = "toolkit_dep",
    source = .{ git = .{
        url = "https://example.com/toolkit.git",
        branch = "main",
    } },
    modules = .[
        .{ name = "Toolkit" },
        .{ path = "packages/codec", name = "Codec_Json", alias = "Json" },
        .{ path = "packages/parser", alias = "Parser" },
    ],
}
```

最后一项只在 parser 包恰有一个公开模块时合法。若 Git 来源根包恰有一个模块，可整体省略 modules；并不统计成员的导出。

```jai
// apps/cli 引用兄弟包；若目标只有一个模块，可省略选择列表。
.{ name = "codec_dep", source = .{ path = "../../packages/codec" } }

// 同一目标也可明确要求工作区成员资格。
.{
    name = "codec_dep",
    source = .{ workspace = true },
    modules = .[ .{ path = "packages/codec", name = "Codec" } ],
}
```

这两个本地示例是替代写法，不能在同一消费包内重复选择同一个 Codec 导出。Git 检出中的 packages/http 可用 source.path = "../codec" 引用同检出的 codec；该引用仍属于原仓库提交，不变成本机任意目录依赖。

### 11. 失败与组合验收表

| 场景 | 必须观察到的结果 |
|---|---|
| 缺来源或同时配置多个来源 | 声明错误，不猜类型 |
| Git 依赖与同名工作区成员共存 | 按 Git 来源，成员不覆盖 |
| 目标没有 package.jai，目录里恰有 module.jai | 普通依赖失败，不隐式包装 |
| 模块路径是文件、绝对路径、越出来源或目标不存在 | 失败，不改用其他位置 |
| 显式导出不存在 | 失败，不选首项或全部导出 |
| 根包零/一/多模块而省略 modules | 分别为无模块错误、唯一选择、歧义 |
| 无根包的工作区，即使只有一个成员而省略 modules | 要求显式成员位置 |
| 普通依赖显式 modules = [] | 能力不匹配，包本身可仍合法 |
| 不同模块的最终导入名重复或仅大小写不同 | 名称冲突，显式 alias 才能区分 |
| 依赖最终导入名覆盖本包模块或编译器标准模块 | 冲突，不按搜索顺序覆盖 |
| 同一实际模块跨引用/alias 重复选择 | 重复错误，不默默合并 |
| path/workspace 同一目录同一导出 | 各自资格校验后仍报重复 |
| path/workspace 同一目录不同导出 | 可并存，仍须通过导入名检查 |
| 同名但不同 Git 来源/提交的包 | 可用不同引用名/alias 并存，不承诺类型互换 |
| 目标路径改为另一个合法包且所选模块有效 | 使用该目标，不比较 Dependency.name 与包名 |
| App 未声明 Crypto，只通过 Http 间接需要它 | Http 可使用；App 不获得直接导入权限 |
| Codec 使用同包 Core，消费方只选择 Codec | Codec 内部可用，Core 不自动对消费方可见 |
| 包依赖形成 A -> B -> C -> A | 报完整环路，不解环 |
| workspace 无所属上下文或目标非成员 | 失败，不降级为 path |
| Git 提供方内部 workspace 与消费方有同名成员 | 只在提供方检出内按成员资格解析 |
| Git 提供方内部 path 指向同检出非成员兄弟包 | 合法并保留原仓库/提交身份 |
| Git 提供方内部 path 或 workspace 归属查找越出检出 | 失败，不使用缓存旁边的目录 |
| URL/选择器无效、修订无法取得 | 失败，不替换来源或提交 |
| 修改别名或添加模块，旧提交不含所选导出 | 失败，不隐式追新 |
| 更新当前工程直接/传递选择 | 其他工程/成员的独立状态不变 |
| 新图获取或校验中途失败 | 当前操作失败，旧状态完整保留，可保留下载内容 |
| 新图已保存但源码编译失败 | 不回滚已完成的解析状态 |
| 状态损坏或不可读 | 明确错误，不自动按缺记录重建 |
| 清理内容缓存后仍有有效选择 | 在线只补原提交；离线缺内容时报错 |
| 删除选择状态或将工程复制到新根 | 新解析；浮动修订可能改变，离线限制仍生效 |
| XDG 值为相对路径 | 警告并用平台默认，不基于 cwd |
| 有效 XDG 目录不可写或无可靠默认用户目录 | 报错，不换到临时/当前/系统根目录 |
| 插件/生成流程需修改共享 Git 源码 | 使用工程私有派生内容，不回写共享检出 |

离线所有直接/传递组合还须满足第 8 节矩阵；版本/来源字段的旧写法须由迁移契约给出诊断，不静默降级。
